# about.shuangyue.space 技术与体验优化报告

> 目标仓库：`shuangyue1124/about`
>
> 目标站点：`https://about.shuangyue.space`
>
> 部署：Cloudflare Pages + Pages Functions
>
> 数据：D1 + KV
>
> 能力：Turnstile + Workers AI
>
> 本报告用于 Coding Agent / Claude Code / Codex 执行优化。
>
> **原则：以现有架构为基础优化，不进行无必要的大规模重构。不要引入 React/Vue/Next.js 等框架，不要把静态站改成 SPA，不要迁移离开 Cloudflare Pages。**

---

# 0. 总体结论

当前项目整体架构合理：

```text
GitHub main
    ↓
Cloudflare Pages Build
    ↓
npm run build
    ↓
public/
    ↓
Pages 静态资源

Pages Functions
    ↓
worker.js
    ├── /api/site
    ├── /api/comments
    ├── /api/events
    └── /api/admin/*
          ↓
       D1 / KV / Workers AI / Turnstile
```

评论系统已经是：

```text
访客
 ↓
Turnstile
 ↓
本地粗过滤
 ↓
Workers AI
 ↓
D1
 ↓
KV approved cache
 ↓
Worker memory cache
 ↓
公开评论
```

这个架构不需要推倒重来。

优化重点应该集中在：

1. API 防滥用
2. D1 事件数据增长控制
3. 管理后台安全
4. API Header 分层
5. 静态 HTML / JS 重复渲染
6. D1/KV 职责进一步明确
7. i18n / 数据一致性
8. 图片与构建性能
9. 自动化检查
10. 旅行内容的数据模型与 UI

# P0 —— 必须优先处理

## P0-1：`/api/events` 没有任何限流，存在 D1 写入滥用风险

文件：

```text
worker.js
functions/api/events.js
```

当前 `/api/events`：

```text
POST /api/events
    ↓
解析请求
    ↓
saveEvent()
    ↓
D1 INSERT
```

没有 Turnstile、没有 IP 限流、没有请求频率限制。

任何人都可以直接大量 POST：

```text
/api/events
```

造成：

- D1 写入量暴涨
- 统计数据污染
- D1 storage 增长
- D1 query 变慢
- Cloudflare 资源消耗
- AI 后台统计数据失真

### 要求

增加轻量级防滥用机制。

优先方案：

```text
/api/events
 ↓
基本请求校验
 ↓
IP / path / event type 限制
 ↓
短时间限流
 ↓
D1
```

对于个人站，不需要做复杂 WAF。

建议：

- 单 IP 每分钟最多允许一定数量事件
- 单请求最多一个 event
- `type` 白名单
- `path` 长度限制已经有，继续保留
- `page/lang` 做有限枚举
- 对明显异常 UA / 超长请求进行拒绝
- 对 page_view 可以考虑采样

### 更推荐

对于访问统计，不需要每一次访问 100% 写 D1。

可以考虑：

```text
page_view
 ↓
采样 / 聚合
 ↓
D1
```

如果未来统计需求增加，可以考虑 Cloudflare Analytics Engine，而不是继续把 D1 当埋点数据库。

### 验收

Agent 必须测试：

```text
正常页面访问 → 正常统计

连续大量 POST /api/events
→ 被限制

随机 type/path
→ 不影响数据库

统计数据仍然正常
```

# P0-2：`/api/comments` 没有独立的请求频率限制

当前评论 POST 已经有 Turnstile：

```text
POST /api/comments
 ↓
Turnstile
 ↓
Workers AI
 ↓
D1
```

这已经很好。

但仍然建议加：

```text
IP rate limit
```

原因：

Turnstile 成功后仍然可能触发：

```text
Workers AI
D1 write
KV refresh
```

攻击者不一定需要绕过 Turnstile，只要能够批量完成挑战，就可能消耗你的 AI / D1 资源。

### 建议

评论接口增加：

```text
同 IP：
1 分钟最多 N 次
10 分钟最多 M 次
```

如果触发：

```text
429 Too Many Requests
Retry-After: ...
```

KV 可以承担短期 rate-limit 状态。

不要把每一次限流都写 D1。

---

# P0-3：管理员登录没有登录失败限流

当前：

```text
POST /api/admin/login
 ↓
读取 ADMIN_PASSWORD
 ↓
verifyPassword()
 ↓
签发 sfsy_admin Cookie
```

密码验证本身使用 SHA-256 + timing-safe compare，session 使用 HMAC 签名，这部分设计是合理的。

但是目前看不到针对：

```text
/login
```

的失败次数限制。

### 风险

攻击者可以持续：

```text
POST /api/admin/login
password=xxxxx
```

进行离线式在线暴力尝试。

### 要求

增加：

```text
login failure rate limit
```

建议：

```text
IP + 时间窗口
```

例如：

```text
5 次失败 / 5 分钟
```

超过后：

```text
429
Retry-After
```

成功登录后清理对应失败计数。

不要把失败记录写 D1。

KV 最合适。

# P0-4：统计事件没有数据生命周期策略

D1 schema 中：

```text
site_events
```

目前不断 INSERT。

已有索引：

```text
idx_site_events_type_created
idx_site_events_path_created
```

但没有看到自动删除旧事件的机制。

这意味着：

```text
1 天
→ 一些数据

1 年
→ 大量数据

几年
→ 统计表越来越大
```

### 建议

个人网站不需要永久保存访问日志。

推荐：

```text
site_events 保留 90 天
```

或者：

```text
30 / 90 / 180 天
```

做成配置。

### 注意

不要简单地在每个 page_view 请求里：

```sql
DELETE FROM site_events WHERE created_at < ...
```

否则会给正常请求增加额外数据库负担。

更推荐：

- 定期任务
- GitHub Actions 定时调用受保护管理接口
- 或其他 Cloudflare 定时机制
- 如果暂时不想加定时任务，至少提供管理员手动 cleanup

# P1 —— 强烈建议处理

## P1-1：API CORS 当前全部 `Access-Control-Allow-Origin: *`

当前：

```text
apiHeaders()
```

统一返回：

```text
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: content-type, authorization, x-admin-action
```

这对于：

```text
/api/comments
/api/site
/api/events
```

未必有问题。

但不应该让：

```text
/api/admin/*
```

也使用同样宽泛的 CORS 策略。

### 建议

拆成：

```text
publicApiHeaders()
adminApiHeaders()
```

公共 API：

```text
Access-Control-Allow-Origin: *
```

管理员 API：

```text
不开放跨域
```

或者只允许：

```text
https://about.shuangyue.space
```

### 重要

不要把这个理解成“当前已经存在严重的管理员 Cookie 泄露”。

管理员 Cookie 使用：

```text
HttpOnly
Secure
SameSite=Lax
```

已经提供了重要的保护。

这里主要是**缩小攻击面和减少未来改代码时误配置的可能性**。

---

# P1-2：Pages `_headers` 不会自动覆盖 Functions 响应

当前 `_headers` 已经配置：

```text
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

静态页面这很好。

但 Cloudflare 官方明确说明：

> `_headers` 不会应用到 Pages Functions 生成的响应。

因此：

```text
/api/*
```

目前主要依赖：

```text
apiHeaders()
```

而 `apiHeaders()` 现在只有：

```text
content-type
cache-control
CORS
```

### 要求

给 API 响应至少加入：

```text
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

如果 API 不需要 iframe：

```text
X-Frame-Options: DENY
```

并考虑：

```text
Permissions-Policy
```

Cloudflare Pages 官方文档明确指出，Pages Functions 生成的响应需要在 Function 中自行添加这些 Header。

# P1-3：API 错误响应不应该直接暴露 `error.message`

当前多个 catch：

```js
return json({
  error: error?.message || "..."
}, 503);
```

这意味着未来某个底层异常：

```text
D1 error
JSON parse error
binding error
Workers AI error
```

可能直接返回给访客。

### 建议

对外：

```json
{
  "error": "service unavailable"
}
```

服务器内部：

```text
console.error(...)
```

最好增加：

```text
requestId
```

例如：

```json
{
  "error": "service unavailable",
  "requestId": "..."
}
```

这样管理员能根据 requestId 查日志。

# P1-4：`ensureSchema()` 不应该成为正常请求路径上的数据库初始化机制

目前 Worker 会在运行时执行：

```sql
CREATE TABLE IF NOT EXISTS ...
CREATE INDEX IF NOT EXISTS ...
```

这属于“自举式 schema”。

优点：

- 本地方便
- 新环境不容易因为忘记 schema 直接炸

缺点：

- D1 热路径存在 DDL 检查
- isolate 第一次请求需要额外数据库操作
- 多个 isolate 同时初始化没有必要
- 数据库 schema 管理不够清晰

仓库已经存在：

```text
migrations/0001_comments_d1.sql
```

说明项目本身已经有 migration 体系。

### 推荐

生产环境：

```text
migration
 ↓
正式 schema
```

运行时：

```text
SELECT / INSERT / UPDATE
```

不要每个 isolate 都执行建表逻辑。

可以保留 bootstrap 代码用于本地开发，但生产最好明确区分。

---

# P1-5：D1 是主配置库时，没必要同时把 `site_config` 写 KV

当前配置：

```text
saveSiteConfig()
 ├── D1
 └── KV
```

但是：

```text
loadSiteConfig()
```

有 D1 时优先读取 D1。

也就是说生产环境：

```text
D1 = 主配置
KV = 几乎没有必要作为配置存储
```

这增加了：

```text
D1 / KV consistency
```

复杂度。

### 推荐

明确：

```text
D1
 ├── comments
 └── site_config

KV
 └── approved comments cache
```

旧 KV：

```text
comments:index
```

只保留 migration 兼容。

配置 KV 可以逐步废弃。

# P2 —— 前端架构优化

## P2-1：目前存在“静态 HTML 已经生成 + app.js 再完整 render 一遍”的重复工作

这是我认为前端最值得改的架构点之一。

项目 build 会生成完整 HTML：

```text
scripts/build-pages.mjs
```

HTML 本身已经有：

```text
hero
nav
travel
city
contact
comments placeholder
```

但是 `assets/js/app.js` 加载后又：

```js
app.innerHTML = layout(renderHome());
```

或者：

```js
app.innerHTML = layout(renderTravel());
```

也就是：

```text
服务器生成 HTML
       ↓
浏览器显示
       ↓
app.js 加载
       ↓
重新生成整个 DOM
       ↓
覆盖 #app
```

这会导致：

- 重复 HTML 构建
- DOM 全量替换
- 不必要的 JS 执行
- 可能产生 CLS
- 用户已经看到内容后又重新构建
- 调试复杂度增加

### 推荐目标

改成：

```text
静态 HTML
 ↓
立即可用
 ↓
JS 只做 enhancement
```

例如：

```text
主题切换
语言辅助
评论加载
搜索
分享
复制
交互
```

而不是：

```text
JS 再生成整个页面
```

```text

文化 → CULTURE_TEST
```

防止模板字段再错位。

并且中文主要走系统字体。

这个方向是正确的。

不要为了视觉一致性把整个中文字体打进仓库。

否则会显著增加首屏体积。

# P2-14：补充 HSTS

当前 `_headers` 有：

```text
X-Content-Type-Options
X-Frame-Options
Referrer-Policy
Permissions-Policy
```

建议增加：

```text
Strict-Transport-Security: max-age=31536000
```

前提：

```text
about.shuangyue.space
```

及相关生产域名已经确认长期 HTTPS。

不要盲目加：

```text
includeSubDomains
```

除非确认 `shuangyue.space` 下所有相关子域都可以接受 HSTS。

# P2-15：考虑 CSP，但不要直接上一条“拍脑袋 CSP”

当前页面存在：

- inline theme script
- JSON-LD
- Turnstile
- 页面 JS
- 图片
- 可能的外部资源

因此不要直接：

```text
Content-Security-Policy: default-src 'self'
```

这样很可能把 Turnstile / 主题 / 其他功能直接搞坏。

正确做法：

1. 统计实际资源来源
2. 移除不必要的外部资源
3. 将 inline theme script 改成 hash/nonce 或外置
4. 然后建立 CSP
5. 先 `Content-Security-Policy-Report-Only`
6. 确认无误后再正式启用

# P2-16：Admin 页面仍然引用外部 QQ 头像

# P3-2：“最新到访”与日本旅记时间可能产生语义冲突
